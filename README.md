# 行程规划 · 可运行原型

选城市 → 先看这座城的**全城三维地图**(所有景点都标在图上)→ 定天数和偏好 → 生成一份**可编辑**的行程草案 → AI 指出安排里的问题。

当前是 Web 版(手机浏览器即可用),用来验证"这套流程到底好不好用"。
验证通过后再决定做不做 Android 原生 —— 届时候选池、编排、提示词这套后端逻辑可以原样复用,
只需要重写 UI 层。

## 目录

```
travel-planner/
  web/index.html      前端原型,单文件,无需构建(含三维地图)
  server/
    app.py            FastAPI 接口
    env.py            .env 加载(会剥掉值两侧的引号)
    amap.py           高德封装(地理编码 / POI 搜索 / 路径规划)
    planner.py        候选池 → 编排 → 时间轴 → 优化建议
    data.py           内置示例数据(没 Key 时用)
    .env.example      改成 .env 后填 Key
    .cache/           磁盘缓存(自动生成,删掉即强制重拉)
    store.py          磁盘缓存读写(景点 / 地理编码 / 路线 / 行程)
    selftest.py       不开服务器也能验证编排逻辑
  README.md
```

## 跑起来

### 方式一:只看界面(不用装任何东西)

双击 `web/index.html`,直接在浏览器里点。此时用的是内置示例数据,
右上角徽标显示"示例数据"。

### 方式二:起后端(推荐,能验证真实链路)

```bash
cd server
pip install -r requirements.txt
uvicorn app:app --reload
```

然后打开 <http://localhost:8000> —— 后端直接托管前端,不用另开服务。
此时前端会自动探测到后端,徽标变成"真实数据"或保持"示例数据"(取决于有没有填 Key)。

单独验证编排逻辑、不开服务器:

```bash
python selftest.py
```

## 地图

底图用**腾讯地图 GL JS**,三维实景(`building3d` + 俯仰角 60°)。两个地方有地图:

**「全城」页**(选完城市的第一站):整座城市的候选景点全铺在图上 ——
标记按类型上色,排进行程的会变成品牌绿;评分最高的 12 个标出名字,其余靠点开看;
视野自动框住全城。右上角胶囊显示当前数量,右下角切「三维 / 俯视 / 旋转」。
下方可以按类型过滤,榜单点一条地图就平移定位过去。

**「地图」页**(生成行程后):两组开关 ——

- **范围**:「当天行程」只画这一天的点和连线;「全城景点」把整座城市的候选点全铺出来
  (灰针 = 全城候选,绿点 = 当天已排),视野自动拉到全城,列表按评分排序、点一条可定位。
- **视角**:「三维」倾斜看楼块 / 「俯视」正北朝上。

点标记可以点开看名称和评分。

坐标系不用换算:高德返回的经纬度就是 GCJ-02,腾讯 GL JS 也是 GCJ-02,直接喂进去就行。

底图 Key 有两种给法:

| 场景 | 怎么拿到底图 |
|---|---|
| 在 WorkBuddy 预览里打开 | 走内置密钥代理(`_TMapSecurityConfig`),前端不落任何 Key,开箱即用 |
| 自己 `uvicorn` 起服务访问 | 需要在 `.env` 里填 `TMAP_KEY`,由 `/api/config` 下发给前端 |

`TMAP_KEY` 去[腾讯位置服务开放平台](https://lbs.qq.com/dev/console/application/mine)免费申请。
不填也不会白屏 —— 会自动退回手画的点位示意图,并在下方说明原因。

## 接入真实数据

把 `server/.env.example` 复制成 `.env`,填入:

| 变量 | 从哪来 | 作用 |
|---|---|---|
| `AMAP_KEY` | 高德开放平台 → 应用管理 → 添加 Key → **服务平台选「Web 服务」** | 换掉示例景点,用真实 POI 和真实通勤时间 |
| `LLM_KEY` | 阿里云百炼 → 右上「密钥管理」 | 换掉规则生成的建议,用大模型输出 |
| `TMAP_KEY` | 腾讯位置服务开放平台 | 只在自己起服务时需要;预览场景不用 |
| `HOTSPOTS` | 填 `0` 关闭,默认开 | 生成行程前联网检索一趟「这阵子什么在火」 |

**`.env` 里的值不要加引号** —— 早期版本因为 `AMAP_KEY="xxx"` 带引号,Key 被原样发出去,
高德返回 `INVALID_USER_KEY`,而 `LIVE` 只看"填没填"所以依然是 True,表现为徽标显示"真实数据"
但候选池是空的。现在加载器会自动剥引号。

只填 `AMAP_KEY` 也行,建议会继续用规则生成。
两个都不填就一直是示例数据 —— 项目零配置也能跑。

重启服务后生效。前端徽标会显示当前数据来源。

### 大模型换成别家

接口用的是 OpenAI 兼容格式,换模型不用改代码,只改 `.env`:

| 想用 | `MODEL_NAME` | `MODEL_URL` |
|---|---|---|
| qwen-plus(默认) | `qwen-plus` | `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` |
| qwen-flash(最便宜) | `qwen-flash` | 同上 |
| DeepSeek | `deepseek-chat` | `https://api.deepseek.com/chat/completions` |

注意 `MODEL_NAME` 里带 `qwen3` 的会自动关掉思考模式(显式加 `enable_thinking=false`),
不然它会先输出一大段推理再回答,慢一倍还容易偏离格式要求。
另外 **Key 和 model name 必须属同一个地域**——国际版 Key 配北京那个 URL 会鉴权失败。

### 当下热点:联网检索

候选池回答的是"这座城市有哪些景点",但回答不了"这阵子什么在火" ——
限时展、新开的打卡地、因为某部剧重新走红的老景点,既搜不到,也不在模型的训练数据里。
实测不开联网时,模型会坚定地认为"现在是 2024 年"而对当下的问题直接拒答。

所以生成行程前会先让模型联网检索一趟,产出带时效性的热点情报后,严格走这三条核实路径:

```
联网提名 → 回查候选池(命中即原地打标)
        → 没命中再拿名字去高德搜(搜到且是真景点才补进池)
        → 两处都查无此地 → 丢弃,只在页面底部留一条「联网线索」
```

每一步都卡死这一条:**模型只能提名,入池由高德说了算。**
联网环节再怎么幻觉,也污染不了行程——福州有没有这个展览,由地图数据决定,不由模型决定。

代价是首次生成行程慢 5~15 秒(情报缓存 6 小时,之后基本无感)。
不是每家供应商都支持联网;若换了供应商报错,`.env` 里写 `HOTSPOTS=0` 关掉,其余功能不受影响。

## 缓存:能存本地的都存本地

查一座城要发 7 次高德搜索(每个关键词一次),生成一次行程还要再叫一次大模型。
所以做了四类缓存,两层存储(后端磁盘 + 浏览器 localStorage):

| 缓存 | 后端磁盘 `server/.cache/` | 前端 `localStorage` | 有效期 | 省下的调用 |
|---|---|---|---|---|
| 城市中心点 | `geo_<城市>.json` | — | 30 天 | 1 次地理编码 |
| 候选景点池 | `pois_<城市>.json` | `tm_pois_<城市>` | 7 天 | 7 次高德搜索 |
| 站间通勤耗时 | `route_<点对>.json` | — | 7 天 | 每次重排十几次路径规划 |
| 完整行程 | `plan_<签名>.json` | `tm_plan` | 12 小时 | 大模型 + 全部路径规划 |
| 当下热点情报 | `hot_<城市>.json` | — | 6 小时 | 一次联网检索 |

后端另有进程内内存缓存(10 分钟),挡同一次会话里的重复调用。

- 只缓存真实数据;示例数据本来就在本地,写缓存没意义。
- **行程也存本地**:重开页面时,上次生成的行程连同参数(城市 / 天数 / 偏好 / 节奏)一起恢复,
  首页会出现「已恢复上次的「西安 · 4 天」行程 · 查看 / 忽略」。参数一旦改过,签名对不上就不恢复。
- 「重新生成」会带 `fresh=true` 跳过后端缓存,重新叫一次大模型;「重新拉取」跳过景点缓存。
- 榜单标题会写明来源,例如「本地缓存 · 3 小时前」。
- 强制清缓存:删 `server/.cache/` 里的 json,或清掉浏览器 localStorage 里 `tm_` 开头的键。
- 写盘 / 写 localStorage 失败一律静默跳过 —— 缓存只是省钱,不是功能的一部分。
  localStorage 配额满了会自动丢掉最旧的三分之一再试一次。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 返回 `live`(是否接高德)和 `model`(是否接大模型) |
| GET | `/api/config` | 下发给前端的非敏感配置(目前只有底图 Key) |
| GET | `/api/pois?city=成都` | 候选池,「全城」页选完城市就调它 |
| POST | `/api/plan` | `{city, days, prefs, pace, fresh?}` → 完整行程;`fresh=true` 跳过缓存 |
| POST | `/api/plan_stream` | 同上,但以 NDJSON **流式**返回阶段进度。**前端默认调这个** |
| POST | `/api/replan` | 用户改完地点后重排并重算时间轴 |

### `/api/plan_stream`:为什么行程要流式返回

一次真实生成要依次经过 **候选池多关键词串行搜索**(还可能撞上高德限流退避)→
**联网检索当下热点** → **大模型编排**(失败还要重试一次)→ **逐段路径规划**,
实测 20~40 秒。如果只有一个普通接口,前端就只能干转圈。

所以接口按行吐 JSON(NDJSON),前端逐行读、实时更新加载界面:

```
{"stage":"pool","detail":"检索景点 3/7 · 已收录 50 个","pct":0.174}
...
{"type":"done","pct":1.0,"plan":{...整份行程...}}
```

阶段划分与大致权重:`pool` 0.02→0.38、`hot` →0.50、`ai` →0.72、`route` →0.95、`save` →1.0。
用 NDJSON 而不是 SSE,是因为 EventSource 只支持 GET,而这个请求要带 `days/prefs/pace/fresh`。

前端的加载遮罩**只在最后一行 `done` 到达、行程页渲染完毕之后**才撤 ——
不会出现"先跳到行程页干等"。后端不支持这个接口时自动退回 `/api/plan`,遮罩照样不提前关。

## 三条设计上的硬规矩

改代码时别破坏这几条,它们是这个方案成立的前提:

1. **景点只能从候选池里挑。** 池子由高德 POI 搜索构建,模型只能从中选择。
   这是防幻觉的根本手段 —— 它没机会编造不存在的地方。

2. **站间耗时必须由路径规划接口算好再喂给模型。**
   `planner.compute_day()` 负责这件事。让模型自己估通勤时间,它一定会编。
   所有数字都预先算好,模型只做推理和表达。

3. **行程必须可编辑。** 换一个、删掉、加一个,改完自动重排。
   不可编辑的 AI 行程,排得再准用户也不会真的用 —— 他没有参与感,出门前会一直犹豫。

## 已知的边界

- **示例数据只有成都、杭州、西安三个城市**(城市格子上带小圆点的就是)。
  没接后端时选其他城市,全城页会明说"还没有可用数据"并把这三座城摆出来;
  填了高德 Key 之后任意城市都能查。
- **候选池来自高德关键词搜索,不是"官方名胜清单"。** 景点判定走白名单制
  (`data.py` 顶部的《景点判定标准》):以「供人观赏、游览、体验」为主要功能、
  游客会专程前往、能停留 30 分钟以上,三条缺一不可;高德 23 个一级分类里
  只有「风景名胜 / 科教文化服务 / 购物服务 / 体育休闲服务」能出景点,
  「商务住宅」(产业园区、写字楼、住宅区)整体否定。
  残留误差主要在边界:与办公楼同名的文创园(源和1916、觅鲤这类)救不出来 ——
  宁可漏一条,也不能把 293 条办公楼放回行程。
- **大学默认不算景点,只有「观光型校园」算。** 普通大学主功能是教学,不满足功能线;
  厦大思明、武大、北大未名湖这类校园本身是游赏对象,按 `data.py` 的 `CAMPUS_SIGHTS`
  名单定向补搜(通用关键词搜不到大学,加「大学/名校/校园」关键词又全是老年大学与
  留学培训)。院系、附中、附属医院一律不收。
- **高德给不了"好不好玩"。** 名称、评分、人均、营业时间能给;建议游玩时长按类型推断,
  室内外也是推断的。所以第一版的诚实定位是"告诉你多远、玩多久、多少钱、评分如何",
  不是"告诉你哪里好玩"。
- **地图上的连线是直线,不是实际道路。** 底图和建筑是真实的,走法不是 —— 画真实路线要接路径规划的折线返回。
- **没有账号、没有历史记录。** 刷新页面行程就没了。这是故意的,先把核心流程验证清楚。
